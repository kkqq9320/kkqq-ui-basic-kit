# Select 키보드 조작 + disabled 시각 표시 — 설계

**작성일:** 2026-08-04
**상태:** 설계 승인 완료, 구현 계획 대기

---

## 1. 목표

Tab으로 `Select`에 포커스한 뒤 **방향키로 열고 값을 고를 수 있게** 한다. 그 과정에서
현재의 ARIA 위반을 바로잡고, **disabled 옵션이 눈에 보이게** 한다.

두 번째 항목은 첫 번째와 분리할 수 없다: 방향키가 disabled 옵션을 건너뛰는데 그게
시각적으로 구분되지 않으면 **"왜 하나를 건너뛰지?"라는 결함으로 보인다.**

## 2. 배경 — 측정된 현황

전부 코드에서 확인한 사실이다.

| 항목 | 현재 상태 |
|---|---|
| 방향키 처리 | **0건.** `Select.tsx`에 `ArrowDown`/`ArrowUp`이 없다 |
| 있는 키 | `Escape`만 (`Select.tsx:89`의 `useEscapeToClose`) |
| 옵션 요소 | `<button type="button" role="option">` (`Select.tsx:257`) |
| 옵션의 tab 순서 | **들어가 있다** — 진짜 `<button>`이라 Tab이 하나씩 훑는다 |
| disabled 옵션 스타일 | **없다.** `.app-select-menu button`(`select.css:32`)에 `:disabled` 규칙이 0건 |
| 저장소 내 선례 | `DateWheelPicker.tsx`에 방향키 처리가 있다 |

**ARIA 위반:** `role="option"`을 개별적으로 tab 가능한 `<button>`에 얹은 것은 WAI-ARIA
listbox 패턴 위반이다. listbox의 옵션은 tab 순서에 개별로 들어가면 안 되고
**roving tabindex 또는 `aria-activedescendant`** 로 관리해야 한다. 옵션이 50개면
Tab을 50번 눌러야 다음 필드로 간다.

`PRINCIPLES.md` §11(접근성)이 이 계약의 상위 근거다.

## 3. 결정 사항

| # | 결정 | 근거 |
|---|---|---|
| D1 | **표준 listbox 패턴으로 바로잡는다** (방향키·Enter·Space·Escape·Home·End) | 소유자 선택. 방향키만 얹으면 ARIA 위반이 남는다 |
| D2 | **타입어헤드는 넣지 않는다** | 소유자가 "표준"을 골랐고 "표준+타입어헤드"는 고르지 않았다. 한글 조합 입력 처리가 별도 고민거리라 범위를 넘긴다 |
| D3 | **끝에서 감싸지(wrap) 않는다** | 네이티브 `<select>`와 같다. APG도 선택사항으로 둔다 |
| D4 | **포커스만으로는 열지 않는다** | 아래 §4에 근거. 소유자가 제안했고 근거를 듣고 철회 |
| D5 | **A/B 두 변형을 만들어 데모에서 보고 정한다** | 이 저장소가 감각이 걸린 결정에 써 온 방식 그대로 — 두 변형을 데모에 토글로 붙이고, 눈으로 보고 고른 뒤, 이긴 쪽만 남긴다 |
| D6 | **disabled는 `opacity: .55` + `cursor: not-allowed`** | 킷 관행(`controls.css:22`, `dialog.css:88`)과 같은 값. 새 토큰도 새 값도 만들지 않는다 |

### D4의 근거 — 포커스만으로 열면 안 되는 이유

소유자가 "Tab으로 포커스되면 아예 열면 어떤가"를 제안했고, 아래 두 가지가 **이 킷의
코드에서 구체적으로** 깨지므로 철회했다.

1. **즉시 무한루프.** `choose()`가 값을 고른 뒤 `restoreFocusWithoutScroll(triggerRef.current, ...)`
   로 **포커스를 트리거에 돌려준다**(`Select.tsx:244`). 포커스가 여는 트리거이면 고르자마자
   다시 열린다. 유령 click용 `suppressReopenRef` 위에 억제 창구를 하나 더 얹어야 하는데,
   그게 키보드 보정이 열 커밋을 먹었던 바로 그 패턴이다.
2. **Tab으로 지나가기만 해도 history 표식이 쌓인다.** `useBackToClose(open, ...)`
   (`Select.tsx:87`)가 열릴 때 `pushState`를 한다(`hooks.ts:304`). Select 3개짜리 폼에서
   제출 버튼까지 Tab하면 표식 3개가 쌓였다 빠진다. 묻힌 표식이 나중에 "빈" 뒤로가기로
   튀어나올 수 있다는 것은 `src/hooks.ts`의 `useBackToClose` 문서가 이미 길게 설명하는
   알려진 트레이드오프다.

얻는 것도 작다 — `↓`가 이미 열므로 아껴지는 건 키 하나인데, 대가는 Tab으로 지나칠
때마다 메뉴가 번쩍이고 아래 내용이 가려지는 것이다. 네이티브 `<select>`도, Radix·
Headless UI·MUI도 포커스만으로는 열지 않는다.

## 4. 키 동작 명세 (두 변형 공통)

### 용어 (혼동 방지)

이 문서에서 두 단어를 구분해서 쓴다.

- **활성(active)** — 지금 방향키로 짚고 있는 옵션. 하이라이트되는 그 하나.
- **선택 가능한(enabled)** — `disabled`가 아닌 옵션. 활성이 될 자격이 있는 것들.

### 닫힌 상태, 트리거에 포커스

| 키 | 동작 |
|---|---|
| `↓` `↑` `Enter` `Space` | 연다. 활성 = **현재 선택된 옵션**, 선택값이 없으면 **첫 선택 가능한 옵션** |

### 열린 상태

| 키 | 동작 |
|---|---|
| `↓` | 다음 **선택 가능한** 옵션을 활성으로. **마지막이면 제자리**(wrap 없음) |
| `↑` | 이전 **선택 가능한** 옵션을 활성으로. **처음이면 제자리** |
| `Home` | 첫 선택 가능한 옵션 |
| `End` | 마지막 선택 가능한 옵션 |
| `Enter` `Space` | 활성 옵션을 선택 → `choose()` → 닫고 트리거로 포커스 복원 |
| `Escape` | 값 변경 없이 닫고 트리거로 복원 (**이미 구현돼 있음**, `Select.tsx:89`) |
| `Tab` | 닫는다. 포커스는 트리거를 거쳐 다음 요소로 (§6.3 참고) |

### 수식키 정책

**`Ctrl` 또는 `Meta`가 눌린 방향키는 무시한다** — 브라우저·OS 단축키를 가로채지 않기
위해서다. 그 외의 수식키는 검사하지 않는다.

이 정책 하나가 `Alt+↓`를 특수 케이스 없이 처리한다. `Alt+↓`(맥은 `Option+↓`)는 네이티브
`<select>`에서 목록을 여는 관례라 습관으로 누르는 사용자가 있는데, `altKey`를 검사하지
않으므로 그냥 `↓`로 처리되어 열린다.

**표에 `Alt+↓`를 따로 적지 않는 이유:** 원래 그 키는 **combobox**(글자를 칠 수 있는
입력칸 + 목록) 패턴에서 `↓`가 캐럿 이동과 겹칠 때 "목록을 열어라"를 구분하려고 있는
것이다. 이 킷의 트리거는 캐럿도 텍스트 편집도 없는 `<button>`이라 겹칠 대상이 없고,
따라서 `Alt+↓`는 `↓`의 중복일 뿐 독립된 계약이 아니다. 나중에 검색 가능한 Select를
만들어 트리거가 편집 가능해지면 그때 이 키가 제 몫을 하게 되고, 그때 근거와 함께
계약에 올린다.

### 경계 조건

- **선택 가능한 옵션이 하나도 없으면**(전부 disabled, 또는 `options=[]`) 방향키는 아무것도
  하지 않는다. `options=[]`일 때 내용 없는 유리 조각이 열리는 것은 **별개의 알려진 결함**
  이며(트리거는 `aria-expanded="true"`인데 메뉴는 약 14px짜리 빈 표면이다) 여기서 고치지
  않는다.
- **disabled 옵션은 활성이 될 수 없다.** 값이 disabled 옵션을 가리키고 있어 열 때의 초기
  활성 후보가 disabled이면, **첫 선택 가능한 옵션**으로 떨어진다.

## 5. 두 변형과 데모 토글

> **결정 (2026-08-05): A(roving tabindex)로 확정했다.** B와 임시 토글은 제거했다.
> 근거는 실기기 측정이다 — 결정을 가른 것은
> 두 가지였다. (1) 터치로 열면 브라우저가 스크립트로 옮긴 포커스에 `:focus-visible`을
> 주지 않아 A의 활성 강조가 안 보이는데, **키보드가 없는 기기에는 "키보드 활성 옵션"이
> 라는 상태 자체가 없으므로** 그때 보이는 선택값의 조용한 처리가 오히려 맞는 표시다.
> 실제 키보드가 있는 환경에서는 A가 `:focus-visible`을 정확히 만족하는 것을 측정으로
> 확인했다. (2) `role="button"` 트리거는 ARIA상 `aria-activedescendant`를 정식 지원하지
> 않으므로 B는 `role="combobox"` 이관을 함께 끌고 온다.
>
> **눈으로 판단하지 않았다.** 옵션 배경색은 140ms 트랜지션 중간에 표본되면 실제 상태와
> 무관한 값으로 읽히고(크로미움은 보간 중 직렬화 표기까지 바꾼다), 실제로 그 오독이 한 번
> 나왔다. 대신 어느 CSS 규칙이 이겼는지를 **이름으로** 보고하는 계측을 데모에 붙여 판정했다
> — 클래스 소속과 의사클래스 매칭은 보간되지 않기 때문이다.

키 동작 로직은 **한 함수를 공유한다.** 갈리는 것은 "활성 옵션을 어떻게 표현하는가"
한 겹뿐이다.

| | **A: roving tabindex** | **B: aria-activedescendant** |
|---|---|---|
| 실제 포커스 | 옵션으로 이동 | 트리거에 머묾 |
| 하이라이트 | 기존 `:focus-visible` **그대로 동작** | `.active` 클래스 신설 + `surfaces.css:24`의 `:is()`에 추가 + `:35-36` reduce 블록도 수정 |
| `tabIndex` | 활성만 `0`, 나머지 `-1` | 전부 `-1` |
| disabled 스킵 | ~~브라우저가 처리(native `disabled`)~~ | ~~직접 구현~~ |
| `Enter`/`Space` | ~~**공짜** — 네이티브 click이 `choose()`를 탄다~~ | ~~직접 처리~~ |
| `Tab` 이탈 | 트리거로 먼저 옮긴 뒤 닫아야 함(§6.3) | 닫기만 하면 됨 |
| 옵션 `id` | 불필요 | **필요** (`useId()`로 생성) |
| 스크린리더 | 옵션을 직접 읽음 | 트리거가 활성 옵션을 읽어줌 |

**취소선 두 줄은 구현하면서 틀린 것으로 드러났다.** 둘 다 A의 비용을 실제보다 싸게
적고 있었다. `Enter`/`Space`는 공짜가 아니다 — 옵션 `<button>`의 네이티브 click이
`choose()`와 겹쳐 열자마자 다시 닫히므로 `preventDefault()`로 막고 직접 부른다.
disabled 스킵도 브라우저가 해주지 않는다: 브라우저가 처리하는 것은 disabled 버튼의
**포커스 가능 여부**이지 방향키 순회가 아니라서, 순회는 직접 구현했고 그 코드는 애초에
두 후보가 공유했다 — 즉 이 줄이 그리던 A/B 차이는 존재한 적이 없다.

**소유자가 눈으로 볼 실제 차이:** `surfaces.css:24`의 호버/포커스 스타일에 `transform`이
걸려 있어, **A에서는 방향키로 훑을 때마다 옵션이 살짝 움직인다.** B에서는 트리거에 포커스
링이 남고 옵션은 조용히 하이라이트된다.

**토글 위치:** `demo/`에만 둔다. `package.json`의 `files`에 `demo/`가 없으므로 소비
프로젝트로 나가지 않는다. 정해지면 **이긴 쪽만 남기고 진 쪽과 토글을 지운다.**

**공통으로 바뀌는 것:** 옵션이 tab 순서에서 빠진다. 지금은 Tab이 옵션 사이를 이동하는데
표준에서는 메뉴를 벗어난다. A·B 모두 동일하며, 이것이 ARIA 위반이 해소되는 지점이다.

## 6. 기존 동작과의 충돌 지점

### 6.1 스크롤 — `scrollIntoView` 금지 계약을 지킨다

`tests/Select.test.tsx:262`가 **"`Element.scrollIntoView`를 절대 부르지 않는다"** 를 명시적
계약으로 고정하고 있다(조상까지 스크롤시켜 다이얼로그 뒤 페이지가 움직이기 때문).
방향키 스크롤도 이 계약을 지켜야 한다 — `menu.scrollTop`을 직접 조작한다.

기존 `scrollSelectedOptionIntoView`(`Select.tsx:50-60`)는 **가운데 정렬**이다. 열 때 한
번이면 맞지만 **방향키마다 가운데로 튀면 거슬린다.** 그래서 "보이면 아무것도 안 하고,
벗어났으면 최소한만 스크롤" 헬퍼를 **따로** 만든다. 기존 함수와 그것을 고정한 6개
scrollTop 테스트는 **손대지 않는다.**

### 6.2 `scrolledToSelectionRef` 가드를 건드리지 않는다

`Select.tsx:223-230`의 가드는 "열려 있는 동안 `position` 재계산마다(포털은 매번 새 객체를
만든다) 사용자가 메뉴 안에서 직접 스크롤한 것을 되돌리지 않기" 위한 장치다. 방향키
스크롤은 **이 경로와 무관한 별도 경로**로 간다. 이 가드를 리셋하거나 통과시키면 그
버그가 되살아난다.

### 6.3 Tab 이탈 — A의 유일한 실질 추가 비용

- **B**: 포커스가 트리거에 있으므로 닫기만 하면 Tab이 자연스럽게 다음 요소로 간다.
- **A**: 포커스가 옵션(포털이면 `body` 끝)에 있어, 그냥 닫으면 포커스한 요소가 언마운트되며
  **포커스가 `body`로 떨어지고 Tab이 문서 처음부터 시작한다.** `keydown` 단계에서
  **트리거로 먼저 포커스를 옮긴 뒤 닫아야** 브라우저가 트리거 기준으로 다음 tabbable을
  계산한다. `keydown`은 기본 Tab 동작보다 먼저 실행되므로 이 순서로 성립한다.

### 6.4 `Escape`는 이미 있다

`Select.tsx:89`가 닫고 `triggerRef.current?.focus({ preventScroll: true })`로 복원한다.
변경 없음. A에서 포커스가 옵션에 있어도 이 복원이 그대로 동작한다.

### 6.5 `choose()`는 그대로 쓴다

값 커밋·닫기·스크롤 스냅샷·포커스 복원·유령 click 억제가 전부 `choose()`에 모여 있다
(`Select.tsx:232-247`). 키보드 경로도 **반드시 이 함수를 지난다.** 우회하면 그 다섯 가지가
조용히 빠진다.

## 7. disabled 시각 표시

### 7.1 규칙

```css
/* css/select.css */
.app-select-menu button:disabled { opacity: .55; cursor: not-allowed; }
```

값은 `controls.css:22`·`dialog.css:88`과 **같다.** 새 토큰도 새 값도 만들지 않는다(§1).
옵션은 배경이 투명하므로 `opacity`는 결과적으로 글씨가 흐려지는 것으로 보인다.

### 7.2 반드시 처리할 특이도 함정

`.app-select-menu button.selected:not(:hover):not(:focus-visible)`(`select.css:34`)가
강조색을 칠하는데, 이것이 `.app-select-menu button:disabled`보다 **특이도가 높다**
(`.selected` 클래스 + `:not()` 두 개 vs `:disabled` 하나). 값이 disabled 옵션을 가리키면
**disabled 표시가 강조색에 먹힌다.**

`16f528a`가 `sidebar.css`에서 겪은 것과 같은 종류의 캐스케이드 사고다.

**해소 방법은 `.selected` 규칙에 `:not(:disabled)`를 더하는 것으로 확정한다.**

```css
.app-select-menu button.selected:not(:hover):not(:focus-visible):not(:disabled) { ... }
```

특이도를 올려 이기려는 쪽(disabled 규칙을 더 무겁게 쓰기)은 특이도 경쟁이 되어 다음
사람이 또 밟는다. `:not(:disabled)`는 **의미가 맞는 쪽**이다 — "선택됐지만 고를 수 있는
경우에만 강조색". 산술은 주석에 남긴다:

```
.app-select-menu button.selected:not(:hover):not(:focus-visible)  = (0,4,1)
.app-select-menu button:disabled                                   = (0,2,1)
```

이 킷은 같은 실수를 이미 한 번 했다(`16f528a`). 새 규칙을 넣을 때마다 특이도를 세는 것이
그 사고의 재발 방지책이다.

### 7.3 확인 방법

데모에 `유로 (EUR)`가 `disabled: true`로 이미 있다(`demo/main.tsx:85`). 별도 픽스처가
필요 없다.

## 8. 테스트 계약

이 브랜치에서 **"실패할 수 없는 테스트"가 여섯 번** 나왔다. 아래 테스트는 전부
**고침을 빼고 실제로 빨개지는지 뮤테이션으로 확인한 것만** 인정한다.

| # | 고정할 계약 |
|---|---|
| 1 | 닫힌 상태 `↓` → 열리고 활성 = 선택된 옵션 |
| 2 | 선택값이 없으면 활성 = 첫 **선택 가능한** 옵션 |
| 3 | `↓`/`↑`가 disabled를 건너뛴다 |
| 4 | 마지막에서 `↓`는 제자리 (wrap 없음) — `↑`도 대칭으로 |
| 5 | `Home`/`End` |
| 6 | `Enter` → `onChange` 호출 + 닫힘 + 포커스가 트리거 |
| 7 | `Escape` → `onChange` **미호출** + 닫힘 + 포커스가 트리거 |
| 8 | `Tab` → 닫힘 + 포커스가 트리거 (§6.3의 함정을 고정) |
| 9 | 옵션이 tab 순서에서 빠진다 — ARIA 위반 회귀 가드 |
| 10 | 활성 옵션이 보이도록 `menu.scrollTop`이 **최소한만** 움직인다 |
| 11 | `scrollIntoView` 여전히 미호출 (**기존 계약 유지**) |
| 12 | **선택 가능한** 옵션이 없으면 방향키가 아무것도 안 한다 |
| 13 | disabled 옵션이 `.selected`여도 disabled 표시가 유지된다 (§7.2 특이도) |
| 14 | `Ctrl+↓`·`Meta+↓`는 **무시**한다 (브라우저 단축키를 안 뺏는다) |
| 15 | `Alt+↓`는 `↓`와 **똑같이** 연다 — 수식키 정책이 이걸 공짜로 처리한다는 증거 |

**초록으로 유지되어야 하는 기존 테스트:** `tests/Select.test.tsx:176-239`의 scrollTop
회귀 6건과 `:262`의 `scrollIntoView` 미호출 계약. 이들은 "열 때 스크롤"의 회귀 가드다.

13번은 CSS 계약이라 vitest가 검증하지 못한다 — `.css?raw` 소스 텍스트로 고정하고,
`AppShell.test.tsx:437`·`Dialog.test.tsx`와 같은 **빈 문자열 가드**를 반드시 같이 넣는다.
