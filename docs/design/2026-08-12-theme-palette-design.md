# 테마 팔레트 — 백업·복원과 앱이 소유하는 저장소

**상태:** 설계. 구현 전.
**출발점:** "색상 변경해 둔 거 백업/복원은 어떻게 돼? 다른 망에서 접속했을 때 내가
설정해 뒀던 색상으로 똑같이 보이게 하려면" (오너, 2026-08-12)

---

## 1. 무엇이 문제인가

### 1.1 `localStorage`는 origin마다 다릅니다

지금 색 설정은 `localStorage["themeColors:light"]` / `["themeColors:dark"]`에만 있습니다.
`localStorage`는 **scheme + host + port마다 별개**라, 기기를 바꾸지 않아도 주소가 다르면
이미 다른 저장소입니다:

```
집에서  http://10.1.1.254:3000
밖에서  https://myapp.example.com     ← 같은 노트북, 같은 브라우저, 다른 저장소
```

그래서 "다른 망에서도 같게"는 **저장 위치를 앱이 정할 수 있어야** 풀립니다.
킷에는 서버가 없으므로 킷이 할 일은 기계를 주는 것까지입니다(PRINCIPLES §14).

### 1.2 토큰 목록을 잊으면 앱의 색이 조용히 사라집니다

`themeTokens.ts`의 함수들은 전부 `tokens: ThemeToken[] = THEME_TOKENS`를 받습니다.
앱이 자기 토큰(`--brand-2` 등)을 더하면 **모든 호출부에 그 목록을 다시 넘겨야** 합니다.
오늘 기준 최소 세 곳 — 편집기의 `groups`, 부팅·테마 전환의 `applyTokenOverrides`,
직접 부르는 `read`/`write`.

**하나만 빠뜨리면 앱이 신설한 색이 말없이 사라집니다.** 실행으로 확인했습니다:

```
확장 목록을 넘기면   readTokenOverrides("light", EXTENDED) → { --accent, --brand-2 }
목록을 안 넘기면     readTokenOverrides("light")           → { --accent }        ← 버려짐
그런데 저장소에는    localStorage["themeColors:light"]      → --brand-2 그대로 있음
```

저장은 됐는데 읽는 쪽이 못 보는 것이고, **경고가 없습니다.** 특히 부팅 시 적용을
잊기 쉽습니다 — 편집기에서는 잘 되는데 **새로고침하면 그 색만 안 돌아옵니다.**

이 상태에서 백업·복원 함수를 더하면 목록을 넘길 자리가 **셋에서 여섯으로** 늘어납니다.

### 1.3 그 밖에 이 용도에서 걸리는 것 셋

- **편집기가 앱이 나중에 적용한 값을 모릅니다.** 마운트할 때 한 번 읽고, 그 뒤로는
  `theme`이 바뀔 때만 다시 읽습니다. 로그인 응답이 늦게 오면 **화면 색은 바뀌는데
  편집기 스와치는 옛 값**입니다. 시크릿 창처럼 로컬 캐시가 빈 상태에서는 반드시 겪습니다.
- **`onChange`가 매 변경마다 불립니다.** 색 피커를 끌면 초당 수십 번입니다. 그대로
  서버로 보내면 안 됩니다.
- **`writeTokenOverrides`에 `try/catch`가 없습니다.** 읽기는 감싸 놓고 쓰기는 안
  감쌌습니다. 저장소가 차단된 환경에서 **색 하나 바꾸면 편집기가 터집니다.**

## 2. 구조 — 목록을 한 번만 묶는다

```ts
const palette = createThemePalette([...THEME_TOKEN_GROUPS, myGroup]);   // 앱이 한 번
```

이후 모든 조작이 이 객체를 지나므로 **토큰 목록을 넘길 자리가 없습니다.** §1.2의
결함이 구조적으로 사라집니다.

| 멤버 | 하는 일 |
|---|---|
| `groups` | 편집기가 그릴 목록(만들 때 받은 것 그대로) |
| `tokens` | 위를 평탄화한 목록 |
| `apply(theme, overrides?)` | `:root`에 적용. 안 넘기면 `read(theme)`을 써서 |
| `read(theme)` | 저장된 덮어쓰기 값 |
| `write(theme, overrides)` | 저장. **성공 여부를 `boolean`으로 돌려줍니다** |
| `serialize(colors?)` | 두 테마를 묶은 백업 값. 안 넘기면 `read`로 읽어서 |
| `parse(input)` | 검증. 부작용 없음 |
| `applyBackup(backup)` | 두 테마에 `apply` + `write` |

**킷 기본 그룹을 자동으로 합치지 않습니다.** 앱이 `[...THEME_TOKEN_GROUPS, ...]`로
명시합니다 — `CUSTOMIZING.md`가 이미 그렇게 가르치고 있고, 암묵적 병합은 "내 목록에
무엇이 들었는가"를 흐립니다.

**기존 함수(`readTokenOverrides` 등)는 그대로 둡니다.** 지우면 breaking이고, 팔레트를
안 쓰는 앱은 지금 그대로 돕니다.

### 2.1 검토했다가 버린 구조

- **매번 `tokens`를 넘기는 지금 방식 유지** — 새 개념이 0이고 일관되지만, 넘길 자리가
  셋에서 여섯으로 늘고 §1.2의 결함이 그대로 남습니다.
- **킷이 전역으로 목록을 기억(`setThemeTokens`)** — 호출부는 제일 깨끗하지만 전역
  상태입니다. 한 페이지에 편집기가 둘이거나 테스트가 서로 오염됩니다.

## 3. 편집기

```tsx
<ThemeColorEditor
  palette={palette}
  theme={theme}
  overrides={fromServer}   // 넘기면 앱이 소유
  onChange={preview}       // 매 변경
  onCommit={save}          // 손을 둔 뒤 한 번
/>
```

### 3.1 `palette` prop

있으면 `palette.groups`로 그리고, 읽기·쓰기·적용도 팔레트의 것을 씁니다.
**`groups` prop은 그대로 둡니다**(지우면 breaking). 둘 다 오면 `palette`가 이깁니다.

### 3.2 `overrides` prop — 저장소 소유권

넘기면 편집기가 **저장하지 않습니다.** 적용하고 `onChange`/`onCommit`으로 알릴 뿐이고
저장은 앱이 합니다. 이것이 로그인 동기화의 핵심입니다 — 서버를 쓰는 앱이 localStorage
쓰기를 당하지 않고, §1.3의 첫 항목(늦게 온 값을 편집기가 모르는 것)도 같이 사라집니다.

**안 넘기면 지금과 완전히 같습니다** — 킷이 읽고 씁니다.

`Sidebar`의 `collapsed` + `onToggleCollapse`와 같은 모양입니다. 이 저장소는 이미
"상태 저장은 쓰는 쪽 책임"을 그 컴포넌트에서 정해 놨습니다.

### 3.3 `onCommit` — 저장 경계

`onChange`는 지금 그대로 매 변경입니다(미리 보기·실시간 적용용).
`onCommit`은 **손을 둔 뒤 한 번**입니다.

**새 경계를 만들지 않습니다.** 편집기에는 이미 세션 개념이 있습니다 — 피커를 끄는
동안을 Undo 한 칸으로 묶으려고 만든 것이고(`EDIT_SESSION_MS = 500`), 포커스가 떠나거나,
버튼을 누르거나, 테마가 바뀌거나, 500ms 쉬면 끝납니다. 사용자가 이미 "한 번의 편집"으로
느끼는 그 지점을 그대로 씁니다. 기존 테스트가 그 경계를 이미 지키고 있습니다
(`포커스가 떠나면 다음 조작은 새 칸이 된다`, `손을 놓고 잠시 쉬어도 새 칸이 된다`).

## 4. 저장 실패

`write`는 `try/catch`로 감싸고 **성공 여부를 `boolean`으로** 돌려줍니다. 읽기와 대칭이
되고, 저장소가 차단된 환경에서 편집기가 터지지 않습니다.

**타입은 안 깨집니다.** `void` → `boolean`은 호출부를 깨뜨리지 않는 것을 실측으로
확인했습니다(그냥 호출, `void` 타입 자리에 대입, 콜백으로 전달 셋 다 통과.
진짜 깨지는 변경을 대조군으로 같이 돌려 그 시험이 무력하지 않은 것도 확인).

**동작은 바뀝니다** — 예전엔 예외를 던졌고 이제 `false`를 돌려줍니다. CHANGELOG의
"고친 것"에 적습니다.

### 4.1 `onPersistError`를 넣지 않기로 한 이유

편집기가 uncontrolled 모드에서 저장에 실패하면 알릴 자리가 없습니다. 그래도 안 넣습니다:

- **저장소가 진짜로 차단되는 경우는 드뭅니다.** 크롬·파이어폭스의 시크릿 창은
  localStorage를 **줍니다**(창을 닫으면 사라지는 세션 저장소). 사파리가 예전에 던지던
  것이 "사생활 모드=막힘"이라는 인상을 남겼지만 지금은 아닙니다. 실제로 막히는 것은
  쿠키·사이트 데이터 전면 차단, 저장소를 끈 웹뷰, 파티셔닝된 서드파티 iframe 정도입니다.
  ⚠️ 이 문단은 **실행으로 확인하지 않았습니다** — 시크릿 창을 띄울 수단이 없었습니다.
- **정작 이 설계의 목표인 로그인 동기화 경로에는 localStorage가 없습니다.** 그쪽은
  controlled 모드라 킷이 저장을 안 하고, 앱은 자기 실패를 압니다.
- 터지는 것은 §4가 이미 막습니다.

아무도 안 꽂는 콜백은 문제를 푸는 척만 합니다. 정말 필요해지면 선택 prop 하나를
더하면 되고, **더하는 것이 빼는 것보다 쌉니다.**

## 5. 백업 형식

```ts
type ThemeColorBackup = {
  version: 1;
  colors: { light: Record<string, string>; dark: Record<string, string> };
};
```

- `palette.serialize(colors?)` — 위 모양으로 묶습니다. 안 넘기면 `read`로 두 테마를
  읽습니다. 기본값과 같은 토큰은 애초에 저장되지 않으므로 백업에도 없습니다.

  ⚠️ **인자가 필요한 이유:** controlled 모드에서는 값이 저장소가 아니라 **앱 상태에**
  있습니다. 읽기만 하면 서버를 쓰는 앱에서 `serialize()`가 **빈 백업**을 돌려줍니다 —
  백업 기능이 정작 백업이 필요한 앱에서 안 도는 것입니다. 그래서 앱이 가진 값을
  넘길 수 있어야 합니다:

  ```ts
  palette.serialize({ light: myLight, dark: myDark })
  ```

- `palette.parse(input: unknown)` — `{ backup, dropped: string[] } | null`.
  **부작용이 없습니다.**
- `palette.applyBackup(backup)` — 두 테마에 `apply` + `write`.

  ⚠️ **`write`가 딸려 있으므로 uncontrolled(킷이 저장하는) 앱을 위한 편의입니다.**
  controlled 앱은 이걸 쓰지 말고 `parse` → 자기 상태에 넣기 → `apply` 순으로 갑니다.
  안 그러면 앱이 소유하기로 한 저장소 밖에 사본이 하나 더 생깁니다.

### 5.1 파싱과 적용을 가르는 이유

**복원은 지금 팔레트를 지우는 파괴적 동작입니다.** 가르면 앱이 덮어쓰기 전에 미리
보여 주거나 확인을 받을 수 있습니다. 그리고 `dropped`가 있어야 **"이 백업의 색 3개는
이 버전이 모르는 것이라 뺐습니다"를 사용자에게 말할 수 있습니다.**

킷은 이미 `readTokenOverrides`에서 모르는 키를 말없이 버립니다. 그건 로컬 캐시라
괜찮았습니다. 백업 파일이나 서버 응답에서 같은 일이 조용히 일어나면 사용자는 색이 왜
안 돌아왔는지 알 방법이 없습니다.

### 5.2 `parse`의 규칙

| 입력 | 결과 |
|---|---|
| 이 팔레트가 아는 토큰 + 유효한 색 | `backup`에 들어감 |
| 모르는 토큰 이름 | 버리고 `dropped`에 이름을 남김 |
| 색 형식이 아닌 값 | 버리고 `dropped`에 이름을 남김 |
| `version`이 1이 아님 | `null` |
| 봉투 모양이 아님(문자열, 배열, `colors` 없음 등) | `null` |

`null`은 **"이건 팔레트 백업이 아니다"**입니다. 빈 백업(`{}` 둘)과 구분됩니다 —
빈 백업은 "덮어쓴 색이 하나도 없는 정상 백업"이고 복원하면 전부 기본값으로 돌아갑니다.

`dropped`는 이름만 담습니다. 버린 이유(모르는 토큰 / 색이 아님)를 나누는 것은 지금
필요가 없어 넣지 않습니다.

## 6. 호환성

| | 기존 소비자가 코드를 그대로 두면 |
|---|---|
| `createThemePalette` 외 새 함수 | 순수 추가 |
| 편집기 `palette`·`overrides`·`onCommit` | 전부 선택 prop. 안 넘기면 **오늘과 동일** |
| `write`의 반환 타입 | 타입 안 깨짐(실측). 던지던 것이 `false`가 됨 |

버전은 **minor**입니다 — 타입은 안 깨지지만 API 표면이 늘고, `write`의 동작이 바뀝니다.

## 7. 테스트로 증명할 것

각 항목은 **고침을 빼면 빨개지는 것을 본 뒤에** 인정합니다.

| | 증명할 것 | 빼면 무엇이 빨개지나 |
|---|---|---|
| 구조 | 팔레트로 만든 모든 조작이 앱 토큰을 본다 | 팔레트가 `tokens`를 안 넘기면 `--brand-2`가 사라짐 |
| A | `overrides`를 넘기면 **저장하지 않는다** | 저장을 지우지 않으면 localStorage에 값이 남음 |
| A | `overrides`가 바뀌면 스와치가 따라온다 | controlled 분기를 없애면 옛 값이 남음 |
| A | 안 넘기면 오늘과 같다 | uncontrolled 경로가 깨지면 기존 테스트가 빨개짐 |
| B | `onCommit`이 세션 끝에 **한 번** | 매 변경마다 부르면 횟수 단언이 빨개짐 |
| C | 저장소가 던져도 편집기가 안 터진다 | `try/catch`를 빼면 렌더가 죽음 |
| C | 실패하면 `false` | 무조건 `true`를 돌려주면 빨개짐 |
| D | `serialize` → `parse` 왕복이 같은 값 | 봉투 모양이 어긋나면 빨개짐 |
| D | `serialize(colors)`가 넘긴 값을 쓴다(저장소를 안 읽음) | 인자를 무시하면 controlled 앱에서 빈 백업이 나와 빨개짐 |
| D | 모르는 토큰은 `dropped`에 이름이 남는다 | 조용히 버리면 목록이 비어 빨개짐 |
| D | `version`이 다르면 `null` | 검사를 빼면 옛 백업을 잘못 읽음 |

⚠️ **jsdom이 못 보는 것:** 적용된 색이 실제로 화면에 그려지는 것. CSS 값 자체는
`:root`의 인라인 스타일로 확인하고, 눈으로 보는 것은 데모에서 합니다.

---

## 8. 단계

리뷰가 가능하도록 둘로 나눕니다.

1. **구조 + C + D** — `createThemePalette`, `write`의 예외 처리와 반환값, 백업 형식.
   컴포넌트를 안 건드립니다.
2. **A + B** — 편집기의 `palette`·`overrides`·`onCommit`. 컴포넌트에 controlled /
   uncontrolled 두 갈래가 생기는 쪽이라 따로 리뷰받습니다.

1이 2에 안 기대므로 1만으로도 백업·복원이 됩니다.

## 9. 이 문서가 정하지 않은 것

- **어느 앱이 어떻게 저장할지.** 킷은 기계까지입니다(§14). 서버 엔드포인트·인증·
  충돌 처리는 앱의 몫이고 이 문서의 범위 밖입니다.
- **여러 기기에서 동시에 고쳤을 때의 병합.** 마지막에 저장한 것이 이깁니다 —
  킷은 병합을 모릅니다.
- **백업 파일의 확장자·MIME.** 앱이 정합니다.
